Software design and engineering

Layered Python architecture

Read original sourceRead enhanced sourceDownload Word narrative

Artifact description

My Grazioso Salvare animal shelter dashboard was created in CS 340 in June 2026. It uses Python, PyMongo, MongoDB, and a Jupyter Dash interface to filter and display animal records for rescue work. The original AnimalShelter class supplied basic create, read, update, and delete operations. I selected this artifact because its existing behavior provided a useful foundation for demonstrating maintainability and security improvements.

Enhancement and demonstrated skills

The software design enhancement separates configuration, database operations, application rules, and errors into config.py, repository.py, service.py, and exceptions.py. CRUD_Python_Module.py now acts as a compatibility facade. This preserves the interface used by the dashboard while moving its internal responsibilities into components that can be reviewed and tested independently.

Environment-based configuration replaces the original notebook's hard-coded credentials. The service validates basic input and blocks empty update and delete queries unless mass changes are explicitly enabled. Custom exceptions provide controlled application errors, and type hints make expected values clearer. Mock repositories allow the service rules to be tested without connecting to the course database. These changes demonstrate modular design, dependency injection through the repository boundary, validation, and maintainable error handling.

Reflection and design trade-offs

The main lesson was that working software can still be difficult to maintain. Keeping every responsibility in one class was simple initially, but it made configuration changes and isolated testing harder. Adding layers creates more files and indirection, so it is a trade-off. In this case, the clearer boundaries justify that complexity because the database enhancement can extend the repository without rewriting the service interface.

A challenge was preserving compatibility with the existing dashboard. Retaining AnimalShelter and its CRUD methods reduced the need to change calling code. Another challenge was balancing safety with flexibility: rejecting empty destructive queries protects the collection, while an explicit mass-change option still supports intentional administrative operations. The existing tests verify these rules. This enhancement is not a complete authorization system or full document-schema validator.

Validation and feedback

All seven supplied service-layer tests passed in the final verification. The tests cover valid create and update behavior, empty-record rejection, read behavior, blocked unrestricted changes, and explicit mass-change behavior. Enhanced Python source files are also checked for syntax. The live dashboard and MongoDB connection require verification in Codio; mock tests do not prove a successful deployment.

The materials supplied for final assembly did not include instructor feedback. I therefore do not claim to have implemented particular instructor comments. The final narrative clarifies the implemented safeguards, test scope, and remaining limitations so that any later feedback can be matched to concrete code changes.

Algorithms and data structures

Prerequisite graph and course ordering

Read original sourceRead enhanced sourceDownload Word narrative

Artifact description

My ABCU course planner originated in CS 300 Data Structures and Algorithms in spring 2026. The original C++ program loads course records, stores them in a binary search tree, displays an alphabetical catalog, and finds a course and its prerequisites. I enhanced it during CS 499 in September 2026. Both versions and the eight-course input file are included so reviewers can reproduce and compare their behavior.

Enhancement and demonstrated skills

I selected this artifact because an alphabetical list is not necessarily a valid prerequisite plan. The enhancement retains the tree for listing and searching and adds a directed adjacency-list graph. An edge connects a prerequisite to a course it unlocks. Hash maps track dependents and indegrees, while a queue holds courses with no unmet prerequisites. Kahn's algorithm processes those courses and releases their dependents. A separate menu option now prints a prerequisite-respecting order.

Validation rejects duplicate course identifiers, unknown prerequisites, repeated edges, self-dependencies, malformed fields, and cycles. The loader validates a candidate catalog before replacing the current one, so an invalid reload preserves previously accepted data. Case-insensitive lookup improves usability. These changes demonstrate graph modeling, queue-based traversal, standard C++ containers, input validation, and integration testing.

Reflection and trade-offs

The most important lesson was choosing structures for the relationships they represent. The tree solves ordered display, and the graph solves dependency planning. Graph construction and topological ordering use expected O(V + E) time with hash-based lookups. The tree is still unbalanced; adversarial insertion order can require O(V squared) total insertion work, and individual lookup can degrade to O(V). Retaining it preserves the original design, but a balanced structure would be a sensible future improvement.

The supplied input has empty trailing columns. I needed to accept those without also accepting a missing prerequisite between populated fields. Preserving valid data after a failed reload was another practical challenge. Building and validating temporary structures before committing the replacement made the user-visible behavior safer. The parser supports the supplied plain comma-separated format; it does not implement quoted CSV fields. The recommended order does not account for term offerings, credit limits, or concurrent enrollment.

Validation and feedback

The enhanced C++17 code compiled with -Wall, -Wextra, and -Wpedantic. The supplied integration checks passed for all eight courses and their prerequisite edges, lowercase search, cycle detection, unknown courses, duplicate courses and edges, and preservation of data after a rejected reload. These checks demonstrate the tested cases rather than exhaustive correctness for every possible input.

No instructor feedback was included in the materials available for final assembly. I have retained the enhancement's documented scope and clarified its algorithmic complexity rather than attributing changes to feedback I cannot verify.

Course outcome alignment

Outcome 3 is demonstrated through graph selection, topological sorting, cycle detection, and complexity analysis. Outcome 4 is supported by a working C++ enhancement and executable integration checks. Outcome 2 is supported by clearer menu labels, setup instructions, and this explanation. Outcome 5 is partially supported through input validation and safe reload behavior; it is not fully established by this classroom planner. Outcome 1 requires the broader coursework reflection and collaboration strategies in the self-assessment.

Databases

MongoDB queries and server-side reporting

Read original sourceRead enhanced sourceDownload Word narrative

Artifact description and purpose

For the database category, I used the same Grazioso Salvare dashboard from CS 340 that I enhanced for software design. The original application connects Python to the AAC MongoDB collection and displays animal records through an interactive table, chart, and map. The October 2026 database enhancement extends the layered architecture with database features, allowing the two categories to demonstrate different skills in one artifact.

Database enhancements

The repository creates three non-unique indexes: idx_animal_id, idx_rescue_filter, and idx_location. The rescue-filter compound index covers animal_type, breed, sex_upon_outcome, and age_upon_outcome_in_weeks. These fields match the dashboard's common filters. Indexes consume storage and add work to writes, so their actual value must be evaluated using query plans and the real dataset. The latitude and longitude index is an ordinary compound index, not a geospatial index, and the existing map callback does not issue geographic range queries.

The read interface supports projections, limits, skip values, and sorting. These capabilities let callers control returned fields and page-sized results. The current notebook still reads all matches into its table and uses client-side pagination; the enhancement does not implement end-to-end server-side table paging. Offset paging can also become expensive at high skip values, so range-based paging would be a future option.

Document counting uses count_documents rather than downloading every matching record. Top-breed reporting uses MongoDB stages for matching, grouping, sorting, limiting, and projecting a compact result for the chart. A separate faceted summary can produce totals and category distributions. These features move reporting work into the database and reduce transferred data for those reporting operations. They do not establish a measured speedup for the entire dashboard.

Security and validation

The enhancement retains environment-based credentials, controlled exceptions, and default protection against empty destructive queries. Read and aggregation limits are validated. These controls reduce accidental broad operations, although the default read remains unlimited and the query interface is intended for trusted application code. A production-facing API would also need authorization, stronger record schemas, query-operator restrictions, and a deployment-specific security review.

All fourteen supplied service and database tests passed in final verification. They check index definitions, counting delegation, aggregation stages, read arguments, limit validation, and the existing service safeguards. Their mocked results demonstrate construction and delegation, not live MongoDB execution or query performance. The actual database, dashboard callbacks, index use, and authentication still require Codio verification.

Reflection and feedback

This work taught me to think beyond successful CRUD calls. Data access also involves how much information crosses the application boundary, where summaries are calculated, and which access patterns indexes support. The layered repository provided a clear place for the database additions while preserving the AnimalShelter facade. That compatibility was useful because the dashboard already depended on the original interface.

A challenge was separating this enhancement from the earlier refactoring. I focused on database execution features rather than counting the same architecture change twice. I also kept the indexes non-unique to avoid imposing an unverified uniqueness constraint on the historical dataset. No instructor comments were supplied for final assembly, so this narrative does not claim particular feedback was incorporated. Final verification instead clarified where implemented capabilities stop and additional integration work begins.

Outcome 3 is supported by the choice of database-side reporting and discussion of index and paging trade-offs. Outcome 5 is supported by secure configuration and guarded data modification, with production limitations disclosed. Outcome 2 is supported by documentation and readable examples.
